# The Flatpak build

Flatpak is the primary public Linux artifact. The AppImage beside it is a
compatibility build.

## Why it is the primary one

electron-builder generates the AppImage's `AppRun` launcher, and that script
adds `--no-sandbox` by itself whenever `unshare -Ur true` fails — with a comment
in its own source saying it prefers the app to start without sandboxing rather
than crash. No electron-builder option reaches it: the same launcher is written
by both the legacy and the static-runtime builders.

Electron's documentation is explicit that `--no-sandbox` disables Chromium's
sandbox for the window and its helper processes and is for testing only. So on
any host without unprivileged user namespaces — a hardened distribution, some
containers — the AppImage would otherwise have run with the sandbox off and said
nothing.

Two things answer that, and the second is why this directory exists:

1. The shell refuses to start when it sees `--no-sandbox`
   (`apps/desktop/src/sandbox.ts`), naming what was detected and what to do.
   Verified by execution: on a machine that genuinely cannot create user
   namespaces, launching `Hermes-0.1.0.AppImage` prints the diagnostic and exits
   non-zero rather than starting.
2. Flatpak sandboxes through bubblewrap and portals instead, needing no SUID
   helper and no unprivileged user namespace of its own. It is the build that
   works *and* stays sandboxed on those hosts.

## Building it

The manifest is generated by electron-builder from the `build.flatpak` block in
`apps/desktop/package.json`, so there is no manifest file here to edit — change
that block instead.

```sh
# once, on the build machine
sudo apt-get install -y flatpak flatpak-builder
flatpak remote-add --if-not-exists --user flathub https://flathub.org/repo/flathub.flatpakrepo
flatpak install --user -y flathub org.freedesktop.Platform//24.08 \
                                  org.freedesktop.Sdk//24.08 \
                                  org.electronjs.Electron2.BaseApp//24.08

# then, from the repository root
cargo build --release -p hermes-cli
(cd frontend && npm run build)
(cd apps/desktop && npm run package -- --linux flatpak)
```

## What is not yet proven

**This build has never been produced.** `flatpak-builder` needs packages that
cannot be installed on the development machine, which has no `sudo`, so the
configuration above is written and unexercised. It is built and smoke-tested on
CI, and until that run exists nothing here should be described as working.

Three things that must be checked the first time it does build, because each is
a real way a Flatpak of *this* application can be broken while still starting:

- **The engine is downloaded at run time and then executed.** If the sandbox
  mounts the data directory `noexec`, `llama-server` will not start. This is the
  highest-risk unknown in the Flatpak work.
- **Paths move.** `directories::ProjectDirs` resolves inside the sandbox, to
  `~/.var/app/ai.hermes.cpu-inference-gateway/`. `HERMES_GATEWAY_HOME` overrides
  it, and the desktop shell already passes that through.
- **Models the user picks from `$HOME` need a `--filesystem=` grant.** The list
  starts narrow, at `xdg-download`. Widen it only when a test asks for it, and
  say in the release notes what is reachable.
